## 목적

**05 가 "코드가 맞는가"를 봤다면 06 은 "이것을 밖으로 내보내도 되는가"를
본다.** 이 페이즈부터 파이프라인이 되돌리기 어려운 일을 한다 — push 는
남의 눈에 보이고, PR 은 알림을 보낸다.

그래서 이 페이즈가 막는 실패는 하나다 — **아무도 승인하지 않은 코드가
나가는 것.** 승인을 대화 속의 "네" 가 아니라 **지문에 묶인 기록**으로 만든
이유가 그것이다. 승인 뒤에 코드가 한 줄이라도 바뀌면 그 승인은 다른 코드에
대한 것이고, 06 은 그것을 자동으로 무효화한다.

## 진입 조건

- 05 가 `passed` 이고 워크트리 지문이 유효하다
- `precheck --phase 06` 이 통과했다 — **05 때와 같은 검사를 다시 돈다.**
  예산과 divergence 는 그 사이에 변한다 (§E13)
- 04 의 백그라운드 전체 회귀가 끝나 있다 (`join_before: "06-pr"`)

## 진입 전에 — 코드는 커밋돼 있어야 한다

**파이프라인은 커밋하지 않는다.** 그런데 `pr` 은 push 를 하고 본문의 diff 통계는
`main...HEAD` 를 읽는다. **미커밋 코드는 push 해도 PR 에 들어가지 않는다.**

커밋 자리는 **`record --phase 05` 통과 뒤, `precheck --phase 06` 전** 하나다.
04 게이트 전에 커밋하면 05 의 변경 파일 목록이 비어 리뷰어 라우팅이 0명이 되고,
`approve` 뒤에 커밋하면 지문이 어긋나 재승인이다.

> **~~알려진 부채 (M25)~~ — 닫혔다 (2026-09-04).** 지문이 `HEAD + 소유 범위
> 미커밋 파일 해시`였을 때는 이 커밋이 04 게이트 영수증을 **반드시** 낡게
> 만들었고, 그래서 06 을 지난 런은 `advance --phase 08` 로 닫히지 않았다.
> 지금 지문은 **소유 범위 파일의 내용 해시**라 커밋이 값을 바꾸지 않는다.
> 커밋 자리가 여기 하나인 이유는 그대로다 — 04 전에 커밋하면 05 의 변경 파일
> 목록이 비고, `approve` 뒤에 커밋하면 승인 지문이 어긋난다.

## 절차

**비용 오름차순이고 첫 실패에서 멈춘다.** 앞의 셋이 무료다.

```
1. precheck --phase 06     정적 · 무료   예산 · 브랜치 · divergence · 인프라
1.5 06_pr_notes.json       너            핵심 흐름 · 직접 확인하는 법 (아래)
2. pr                      정적 · 무료   브랜치 · 조인 · 흐름 노트 · 원격 · non-FF
3. (승인이 없으면 여기서 exit 9 로 정상 종료한다 — stdin 을 붙잡지 않는다)
4. approve --phase 06      사람          지문 + 등급을 함께 못박는다
5. pr                      git           본문 + 마스킹 → push → 계약 삭제
6. forge 도구              너            06_pr_req.json 대로 PR 생성/갱신
7. record --phase 06       제출          PR 번호와 상태를 되돌려 준다
```

### 1·2번 — 모델을 부르지 않는다

```bash
python scripts/pipeline/cli.py precheck --scope pr --phase 06 --run-id {run_id}
python scripts/pipeline/cli.py pr --run-id {run_id}
```

- **exit 3** — 브랜치가 규약과 안 맞거나 보호 브랜치 위다. **브랜치를 자동으로
  만들지 마라.** 어디에 커밋할지는 사람이 정한다
- **exit 9** — 사람의 판단이다. 승인 미응답이거나 원격이 없다(3지선다).
  **상태를 잠그지 않는다.** 답을 받고 `--resume` 으로 잇는다
- **exit 10** — non-fast-forward 다. **force-push 는 금지**이므로 자동 해결이
  없다. 원격 스레드와 승인이 깨진다 (§E8)
- **exit 6** — 승인 뒤에 소스가 바뀌었다. 재승인하고 다시 친다

### 1.5번 — 흐름 노트는 네가 쓴다 (ADR-H058 추기)

PR 본문 `## 작업 내용` 은 **핵심 흐름 → 직접 확인하는 법 → 무엇이 검증됐나(기계) →
05 리뷰 한 줄(기계) → 계약 상세(맨 끝, 접힘)** 순서다. 앞의 둘은 네가
`{run_dir}/06_pr_notes.json` 으로 쓴다:

```json
{"schema":1,
 "flow":[{"step":"채널 정책에 따라 본문·해시태그를 만든다","refs":["formatForChannel"]}],
 "verify":["POST /api/contents 로 초안을 만들고 미리보기에서 해시태그를 본다"]}
```

- `flow` 는 한 단계 이상, 단계마다 `refs` 가 하나 이상이다. **`refs` 만 대조한다** —
  유닛·화면 심볼, 오류 어휘, 데이터 형태, 진입점(`METHOD /path`), 컨테이너 경로처럼
  계약이 이름 붙인 것이어야 한다. `step` 산문은 검사하지 않는다
- `verify` 는 리뷰어가 손으로 따라 할 확인법이다. 한 줄 이상
- 없거나 틀리면 `pr` 이 **exit 8** 로 문제를 이름으로 알린다. 고치고 같은 명령을 다시 친다.
  `no_contract` 런은 선택이고, 닫힌 런(`done`)의 재실행은 대조하지 않는다

### 5번 — 계약을 지우는 것은 여기 한 번뿐이다

04 의 귀속과 05 의 대조가 계약을 계속 읽으므로 삭제 시점을 **push 직전까지**
미룬다. 더 일찍 지우면 재개가 계약을 못 찾고 03 부터 다시 돈다.

### 6번 — PR 은 네가 만든다. 실행기가 아니다

실행기는 `git` 까지가 손이다. `06_pr_req.json` 을 읽고 **forge 도구로**
PR 을 만들거나 갱신한다.

- 본문은 `06_pr_body.md` 를 **그대로** 쓴다. **다시 조립하지 마라** — 그 파일은
  이미 마스킹을 거쳤고, 네가 새로 쓰면 그 마스킹을 우회한다
- `action` 이 `update` 면 **생성하지 말고 갱신한다.** 새로 만들면 PR 이 둘로
  갈라지고 외부 리뷰 스레드가 흩어진다
- **머지하지 마라.** 이 파이프라인의 범위는 PR 까지다

## 제출 형식

`{run_dir}/06_pr_result.json` 하나를 내고 `record --phase 06` 을 부른다.

```json
{"number": 231, "url": "https://github.com/{owner}/{repo}/pull/231",
 "state": "open", "action": "created"}
```

- `number` 는 **정수**다. 문자열이면 exit 8
- `state` 는 `open` · `closed` · `merged` 셋뿐이다
- 이미 `state.pr.number` 가 있는데 **다른 번호를 내면 exit 8** — 갱신이어야
  할 것을 새로 만들었다는 뜻이고, 그것을 통과시키면 07 이 어느 PR 을 볼지
  모르게 된다

## 금지

- **승인을 네가 대신하지 마라.** 이유: `--auto` 는 사람이 미리 켜 두는
  것이지 모델이 고르는 것이 아니다. 승인 없이 push 하면 이 페이즈의 존재
  이유가 없어진다
- **force-push 하지 마라.** 이유: 외부 리뷰 스레드와 승인이 깨진다. non-FF 는
  수정이 아니라 에스컬레이션이다
- **자동으로 리베이스하거나 범위를 쪼개지 마라.** 이유: 히스토리와 범위는
  사람의 것이다. exit 9 는 그 판단을 기다리는 신호다
- **원격이나 base 브랜치를 자동으로 만들지 마라.** 이유: 없다는 것이 사실이고,
  3지선다는 그 사실을 사람에게 보이려는 것이다 (§P3)
- **본문을 다시 조립하지 마라.** 이유: `06_pr_body.md` 는 마스킹을 거쳤다.
  새로 쓰면 비밀값이 그대로 나간다
- **머지하지 마라.** 이유: 명세가 머지 자동화를 범위 밖으로 둔다

## 실패 시

| 무엇 | 분류 | 어떻게 |
|---|---|---|
| `precheck` 예산 초과 · base behind | 정책 | **exit 9.** 자동 분할·자동 리베이스 금지 |
| `infra_preflight` 프로브 실패 | infra | exit 10 · **카운터 미소모** · 에스컬레이션 |
| 브랜치 패턴 불일치 · 보호 브랜치 위 | 정책 | **exit 3. 브랜치를 자동 생성하지 않는다** |
| 백그라운드 회귀 미완 | 정책 | exit 3 — 끝나기 전에 push 하지 않는다 |
| 흐름 노트 없음 · `refs` 가 계약 밖 | 형식 | **exit 8** — 문제를 이름으로 알린다. `06_pr_notes.json` 을 고치고 `pr` 을 다시 친다 |
| 원격 없음 · base 브랜치 없음 | 정책 | **exit 9 3지선다** (§P3). ② 를 고르면 등급 `PASS_WITH_GAPS` |
| 원격 브랜치 non-fast-forward | 정책 | **force-push 금지 → 에스컬레이션** (§E8) |
| 승인 미응답 | — | **exit 9 로 정상 종료.** stdin 을 붙잡지 않는다 → `--resume` |
| 승인 후 코드 변경 | 정책 | 지문 불일치 → **exit 6** → 재승인 |
| push 실패 | infra | 원격 ref 조회로 **push 여부를 확정해 기록**한 뒤 에스컬레이션 |
| forge 도구 불통 | infra | 카운터 미소모 · 에스컬레이션. **push 는 이미 됐을 수 있다** |
| PR 생성됐는데 이후 실패 | — | `state.pr.number` 를 기록해 뒀다 → 재개 시 **생성 금지, 갱신만** |
| 전체 회귀 실패 | 판단 | **push 이전에** 멈추고 04 로. 승인은 지문과 함께 무효화된다 |
| secret 파일 부재 | — | 패턴 마스킹만 적용 + 원장 기록. **경고이지 실패가 아니다** |

**명세 미규정 둘 — 지어내지 않고 적어 둔다.** ① 06 의 절차를 어느 커맨드가
집행하는지 명세의 CLI 표에 없다. `approve` 가 별도 커맨드인 것과 같은 형태로
`pr` 을 두었다. ② `approve --revoke` 의 설명 절이 없다 — `granted: false` 로
되돌리고 사유를 남기는 최소 구현이다.
